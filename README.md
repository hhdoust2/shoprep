# پنل پاسخ‌دهی پیام مشتری

پنل تک‌فروشگاهی برای کمک به فروشندگان فروشگاه‌های کوچک در پاسخ به پیام مشتری.
هر دیپلوی این پروژه فقط برای **یک فروشگاه** است؛ برای پایلوت دو فروشگاهی، دو
دیتابیس Turso و دو پروژه‌ی Vercel جدا از روی همین یک ریپو ساخته می‌شود.

## پشته‌ی فنی

- Next.js 14 (App Router) + TypeScript + Tailwind
- Turso (libSQL، سازگار با اسکیوالایت) به‌عنوان دیتابیس — چون فایل سیستم
  توابع سرورلس Vercel فقط-خواندنی و ناپایدار است، یک فایل `.db` محلی روی
  Vercel بین درخواست‌ها/دیپلوی‌ها پاک می‌شود. Turso همان دیالکت SQL را
  به‌صورت میزبانی‌شده و پایدار ارائه می‌دهد.
- فراخوانی مدل هوش مصنوعی از طریق OpenRouter (فرمت سازگار با API اوپن‌ای‌آی)
  با یک مدل رایگان (پسوند `:free`) — فقط از سمت سرور، کلید هرگز به مرورگر
  نمی‌رسد.

## نکته مهم درباره این محیط

این پروژه در محیطی بدون دسترسی به اینترنت نوشته شده، پس `npm install` و اجرای
واقعی آن تست نشده‌اند. پیش از استفاده در پایلوت واقعی، حتماً یک بار `npm run
build` را لوکال اجرا کنید تا خطاهای احتمالی نسخه‌ی بسته‌ها زودتر دیده شوند.

## راه‌اندازی محلی

```bash
npm install
```

### ۱) ساخت دیتابیس Turso

```bash
turso db create shop-panel-<نام-فروشگاه>
turso db show shop-panel-<نام-فروشگاه> --url
turso db tokens create shop-panel-<نام-فروشگاه>
```

مقادیر خروجی را در `TURSO_DATABASE_URL` و `TURSO_AUTH_TOKEN` قرار دهید.

### ۲) فایل محیطی

```bash
cp .env.example .env.local
```

- `ADMIN_PASSWORD_HASH`: با `npm run gen:hash -- "رمز-دلخواه"` بسازید.
- `SESSION_SECRET`: با `npm run gen:secret` بسازید.
- `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN`: از مرحله‌ی قبل.
- `OPENROUTER_API_KEY`: یک حساب رایگان در openrouter.ai بسازید و کلید بگیرید.
  `OPENROUTER_MODEL` را روی یکی از مدل‌های دارای پسوند `:free` نگه دارید —
  فهرست این مدل‌ها در openrouter.ai/models (فیلتر Free) به‌مرور تغییر
  می‌کند، پس قبل از اجرا آن را چک کنید.

### ۳) ساخت جدول‌ها روی Turso (اختیاری ولی توصیه‌شده)

```bash
export TURSO_DATABASE_URL=...
export TURSO_AUTH_TOKEN=...
npm run init-db
```

اگر این مرحله را رد کنید، همان جدول‌ها به‌صورت خودکار و idempotent در اولین
درخواست به هر مسیر API هم ساخته می‌شوند (`ensureSchema` در `src/lib/db.ts`).

### ۴) اجرا

```bash
npm run dev
```

## دیپلوی روی GitHub + Vercel (فاز تست)

1. ریپو را در GitHub بسازید و پوش کنید. `.env.local` هرگز پوش نمی‌شود
   (در `.gitignore` است).
2. در Vercel، پروژه را از همان ریپو ایمپورت کنید.
3. در تنظیمات پروژه‌ی Vercel → Environment Variables، همان مقادیری که در
   `.env.local` دارید را ست کنید (`ADMIN_PASSWORD_HASH`, `SESSION_SECRET`,
   `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `OPENROUTER_API_KEY`,
   `OPENROUTER_MODEL`, `DAILY_MESSAGE_CAP`).
4. Deploy بزنید.
5. برای فروشگاه دوم پایلوت، مراحل ۱ تا ۴ را با یک دیتابیس Turso جدید و یک
   پروژه‌ی Vercel جدا (یا همان ریپو با env متفاوت) تکرار کنید.

## ساختار داده

- `store_card`: یک ردیف با `id = 1`. پس از اولین ذخیره، `locked = 1` می‌شود
  و مسیر `POST /api/card` هر درخواست بعدی را با خطای ۴۰۳ رد می‌کند — یعنی
  «هفت فیلد کارت تا پایان پایلوت قفل است» در سطح سرور هم اجرا می‌شود، نه
  فقط در رابط کاربری.
- `interaction_log`: به‌ازای هر بار تولید پیشنهاد (`POST /api/suggest`) یک
  ردیف با پیام مشتری و سه پیشنهاد خام (`suggestions`، JSON) ساخته می‌شود.
  همین ردیف، شمارنده‌ی سقف روزانه را هم تشکیل می‌دهد. وقتی فروشنده یکی از
  پاسخ‌ها را کپی می‌کند (`POST /api/log-copy`)، همان ردیف با متن نهایی و
  پرچم «بدون ویرایش» به‌روزرسانی می‌شود.
- پرچم «بدون ویرایش» **سمت سرور** با مقایسه‌ی متن نهایی با سه پیشنهاد
  ذخیره‌شده محاسبه می‌شود، نه بر اساس ادعای کلاینت — چون این عدد، شاخص اصلی
  سنجش کیفیت پایلوت است.
- یک جدول کوچک اضافه (`login_state`) نگه‌دارنده‌ی شمارنده‌ی تلاش‌های ناموفق
  ورود و زمان قفل است، تا این محدودیت بعد از ری‌استارت سرور هم پایدار بماند.

### محاسبه‌ی شاخص پایلوت

```sql
SELECT
  COUNT(*) FILTER (WHERE selected_reply IS NOT NULL) AS total_replies,
  SUM(no_edit_flag) AS unedited_replies,
  ROUND(
    100.0 * SUM(no_edit_flag)
    / NULLIF(COUNT(*) FILTER (WHERE selected_reply IS NOT NULL), 0),
    1
  ) AS unedited_percent
FROM interaction_log;
```

این کوئری از طریق `turso db shell <db-name>` یا هر کلاینت SQL دیگر روی Turso
قابل اجراست.

## ساختار پروژه

- `middleware.ts` — محافظت همه‌ی مسیرها (به‌جز `/login` و `/api/login`) بر
  اساس کوکی نشست امضاشده
- `src/lib/db.ts` — اتصال Turso و تعریف جداول (idempotent)
- `src/lib/session.ts` — امضا/اعتبارسنجی کوکی نشست با Web Crypto (سازگار با
  Edge middleware و Node.js route handlers)
- `src/lib/dailyLimit.ts` — شمارش پیام‌های امروز و مقایسه با سقف
- `src/lib/prompt.ts` — ساخت پرامپت از کارت فروشگاه
- `src/lib/modelClient.ts` — تماس با مدل (فقط سمت سرور)
- `src/app/api/*` — چهار مسیر سروری (ورود، کارت، تولید پیشنهاد، ثبت کپی)
- `src/app/` و `src/components/` — دو صفحه‌ی رابط (پیشنهاد پاسخ، کارت
  فروشگاه) و کامپوننت‌های مشترک
- `scripts/init-db.mjs` — ساخت یک‌بار جدول‌ها روی Turso پیش از اولین دیپلوی
- `scripts/hash-password.js` — ساخت هش bcrypt از رمز عبور دلخواه

## محدودیت‌های عمدی (طبق طرح اولیه)

- هفت فیلد کارت فروشگاه تا پایان پایلوت قفل است (اجرا هم در UI و هم در API).
- سقف صد پیام (تولید پیشنهاد) در روز، پیش از تماس با مدل بررسی می‌شود.
- ورود تک‌کاربره با رمز هش‌شده (bcrypt) و قفل موقت پس از ۵ تلاش ناموفق پیاپی
  (۱۵ دقیقه).
- کلید مدل فقط در مسیرهای سروری (`src/app/api/*`) استفاده می‌شود و هرگز به
  کامپوننت کلاینتی پاس داده نمی‌شود.
- طراحی برای تک‌فروشگاه در هر استقرار است؛ دو فروشگاه پایلوت یعنی دو دیپلوی
  جدا، نه دو تننت در یک دیپلوی.
